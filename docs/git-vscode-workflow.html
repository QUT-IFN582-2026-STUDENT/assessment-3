Git and VS Code Workflow

Beginner guide for the IFN582 assessment repository

Repository: https://github.com/Garyn-QUT/ifn582-assessment-3.git

Team branches: dev is the integration/default working branch. master is a separate branch and is not the target for normal student pull requests.

The basic idea: download the repository once, update your local copy from dev , do your work on a feature branch, commit it, push that branch to GitHub, and open a pull request from your feature branch into dev .

1. Install Git on Windows

  1. Open https://git-scm.com/install/windows.
  2. Download Git for Windows and run the installer.
  3. The default installer choices are suitable for this workflow. Ensure Git is added to the command line/PATH when prompted.
  4. Restart VS Code after installation.
  5. Open PowerShell, Git Bash, or the VS Code terminal and check the installation:
git --version

You should see a Git version such as git version 2.x.x .

Configure your Git identity

After restarting VS Code and opening PowerShell, Git Bash, or the VS Code terminal, configure the name and email Git records on every commit. Use the email address connected to your GitHub account, or your GitHub-provided private email address if you do not want to expose your personal email. 

git config --global user.name "Your Full Name"
git config --global user.email "your-email@example.com"

Check that Git saved the settings:

git config --global user.name
git config --global user.email
Important: user.name is the name displayed on your commits; it is not necessarily your GitHub username. The email should match an email verified on GitHub if you want GitHub to associate the commit with your account.

You also need a GitHub account with access to the repository. For HTTPS authentication, GitHub may ask you to sign in through a browser or credential manager. GitHub does not accept an ordinary account password as a Git password; use the sign-in prompt or a personal access token if requested.

2. Clone the repository

Cloning makes a complete local copy of the GitHub repository. Run these commands in the parent folder where you keep your course work: 

  cd "C:\Users\\IFN582"
  git clone https://github.com/Garyn-QUT/ifn582-assessment-3.git
  cd ifn582-assessment-3

Check that the repository is connected to GitHub:

git remote -v
git status

The remote normally has the name origin . The origin URL should be the repository URL above.

3. Start from the latest dev branch

Run this whenever you begin work or before creating a new feature branch:

git fetch origin
git switch dev
git pull --ff-only origin dev
Do not skip this check: never start new work with uncommitted changes on dev . Run git status . If it reports changes you did not intend to handle yet, ask the team before continuing.

4. Create a local feature branch and its remote branch

Choose a descriptive branch name, for example feature/donation-form or fix/login-validation : 

git switch -c feature/your-short-description

This creates and switches to a local branch. Make your code changes, then save the files.

At this point the branch exists only on your computer. Create its remote branch on GitHub by pushing it: 

git push -u origin feature/your-short-description

The -u option sets the upstream connection. Later, while on this branch, you can usually use just git push and git pull .

Term Meaning
dev Shared integration branch where reviewed work is combined.
local branch Your branch stored on your computer.
remote branch A branch stored on GitHub, such as origin/feature/donation-form .
origin The short name for the GitHub repository you cloned.

5. Review and commit your changes

Before committing, inspect what changed:

git status
git diff

Run the project tests or start the application as required by the assessment. Then stage only the files that belong to this task: 

git add path/to/file.py path/to/template.html

Or stage all changed files if you have checked every change carefully:

git add .

Review the staged version and create a clear commit:

git diff --staged
git commit -m "Add donation form validation"
A commit is local. It records a safe checkpoint on your computer. It does not appear on GitHub until you push it.

6. Keep your feature branch up to date with dev

Before opening a pull request, and whenever the team tells you that dev has changed, merge the latest dev into your feature branch: 

git switch feature/your-short-description
git fetch origin
git merge origin/dev

If the merge completes automatically, run tests and push the result:

git push

This is the normal direction: dev into your feature branch . Do not merge your feature branch into dev locally as a substitute for a pull request unless your team explicitly asks you to.

7. Resolve a merge conflict in VS Code

A conflict means Git found edits to the same lines and cannot choose automatically. The merge is paused until you decide what the final code should be.

  1. Start the merge from the VS Code integrated terminal:
git fetch origin
git switch feature/your-short-description
git merge origin/dev
  1. In VS Code, open Source Control . Conflicted files appear under Merge Changes . Select a file to open the Merge Editor.
  2. For each conflict, choose Accept Current Change to keep your feature-branch version, Accept Incoming Change to keep the incoming dev version, or Accept Both Changes when both pieces belong. You can also edit the result directly.
  3. Read the resulting file as normal code. Make sure imports, indentation, brackets, HTML, and business logic are correct. The final file must not contain markers such as <<<<<<< , ======= , or >>>>>>> .
  4. Save the file. In Source Control, stage it with the + button, or run: 
git add path/to/conflicted-file.py
  1. When every conflict is staged, finish the merge:
git status
git commit -m "Merge dev into feature/your-short-description"
python -m compileall culturemusic
git push
Do not run git commit until every conflict is resolved. If you need to abandon the in-progress merge before committing, use git merge --abort . This returns the branch to its state before the merge.

8. Configure VS Code as Git's merge tool

VS Code's built-in Merge Editor is usually the easiest option. You can also configure Git so git mergetool opens conflicts in VS Code: Use 'single quote' on PowerShell or "double quotes" on Git Bash for 2nd line. 

git config --global merge.tool vscode
git config --global mergetool.vscode.cmd "code --wait --merge $REMOTE $LOCAL $BASE $MERGED"
git config --global mergetool.keepBackup false

When a merge conflict exists, launch the tool with:

git mergetool

The VS Code Merge Editor shows:

  • Incoming or REMOTE : the version coming from dev .
  • Current or LOCAL : your feature-branch version.
  • Result : the file Git will keep after you save it.

Save and close the editor when the result is correct, then stage and finish the merge:

git add path/to/file
git status
git commit -m "Resolve merge conflict with dev"
git push

If the command reports that no tool is configured, use the Source Control Merge Editor described in the previous section. It performs the same choices without requiring a command-line tool configuration.

9. Push and create a pull request into dev

Make sure your feature branch is current, committed, and tested:

git status
git log --oneline --decorate -5
git push
  1. Open the repository on GitHub .
  2. GitHub may show a banner for your recently pushed branch. Select Compare & pull request . Otherwise open Pull requests , select New pull request , and choose your feature branch as the source.
  3. Set the base repository and base branch to dev . The comparison should be your-feature-branch -> dev .
  4. Write a useful title and description. Include what changed, how you tested it, and any known limitations.
  5. Review the changed files and confirm there are no accidental files or secrets. Select Create pull request .
  6. Respond to review comments by editing locally, committing, and running git push . New commits automatically appear in the open pull request.
  7. After the pull request is merged, update your local dev branch before starting the next task: 
git switch dev
git pull --ff-only origin dev
git branch -d feature/your-short-description

Deleting the local branch is optional. Delete the remote branch from GitHub only after the pull request is merged and your team agrees.

10. Quick daily checklist

When Commands
Start work git switch dev
git pull --ff-only origin dev
git switch -c feature/name
Before commit git status
git diff
git add .
git diff --staged
Save work on GitHub git commit -m "Describe the change"
git push -u origin feature/name
Update from dev git fetch origin
git merge origin/dev
Resolve conflicts, test, then git push
Check where you are git branch --show-current
git status

Common mistakes

  • “I committed, but GitHub did not change.” You probably forgot git push .
  • “My branch is not on GitHub.” Push it with git push -u origin branch-name .
  • “I am on the wrong branch.” Check git branch --show-current before editing or committing.
  • “Git says I have conflicts.” Open every file under Merge Changes, resolve it, stage every resolved file, then commit.
  • “I merged the wrong thing.” Stop and ask the team before pushing. Do not delete or reset shared branches.
  • “Git wants a username/password.” Complete the GitHub sign-in flow or configure the approved GitHub authentication method; do not share credentials.
